# Latency budget

Generated by `python3 analysis/budget.py` with the defaults that match `src/config.hpp`. Re-run it after changing any assumption; never edit the numbers by hand.

Assumptions: urban AEB design speed 50 km/h (13.9 m/s); 6 m/s² deceleration (about 0.6 g on dry asphalt); 250 ms brake-pressure build-up; 10 Hz lidar; 60° forward sector; 0.2 m voxels; 40 m region of interest.

## 4. Compute targets (stated before any code is measured)

Rule: compute latency at p99.9 may cost at most one third of a voxel (6.7 cm) of travel at design speed, so latency can never be what flips a decision the grid resolution would not. That is 4.80 ms, rounded down to whole milliseconds:

| quantile | target | why |
|---|---|---|
| p50 | <= 1 ms | 1% duty cycle of one core at 10 Hz; leaves the core for decode and I/O |
| p99 | <= 2 ms | tail no worse than 2x median before OS jitter is added |
| p99.9 | <= 4 ms | 5.6 cm at 50 km/h: inside the voxel/3 rule and the 33 ms system-delay slack |

## 5. Consequences

- At 90 km/h the braking distance alone (52 m) exceeds the 40 m ROI, so this configuration is an urban design. Highway speed needs a longer ROI and a longer-range sensor, not faster code.
- Waiting for the full frame would cost 100 ms of data age (1.39 m), 25 times the 4 ms p99.9 compute budget. The sector trigger is the biggest latency decision in the system.
